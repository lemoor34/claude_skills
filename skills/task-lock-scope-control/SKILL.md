## Назначение
Этот skill — не доменный эксперт, а защитный слой поверх других skills и инструментов.

Его задача: удерживать исходную цель пользователя от первого шага до финальной выдачи результата.

Использовать перед любой нетривиальной задачей, особенно если:
- требуется создать или изменить файл/артефакт;
- есть конкретный формат результата (PDF, DOCX, PPTX, код, сайт и т.п.);
- пользователь указал конкретный логотип, фото, QR, документ, шаблон или иной исходник;
- работа состоит из нескольких tool-calls;
- задача уже получила поправку от пользователя;
- есть риск уйти в побочную проблему или заменить требование «похожим» решением.

## Главный принцип

> Не оптимизируй под «закончить хоть как-нибудь». Оптимизируй под точное выполнение зафиксированного результата.

Красивый промежуточный результат не компенсирует невыполненный hard constraint.

---

## 1. TASK LOCK

До первого существенного действия зафиксируй внутренне:

```text
GOAL: что пользователь в действительности хочет получить.
DELIVERABLE: конкретный конечный результат.
HARD CONSTRAINTS: требования, которые нельзя менять без разрешения.
EXACT ASSETS: конкретные файлы/логотипы/фото/QR/шаблоны, если они есть.
ACCEPTANCE CRITERIA: как проверить, что задача действительно выполнена.
OUT OF SCOPE: найденные по пути задачи, не блокирующие основной результат.
```

Не обязательно показывать этот блок пользователю. Он должен управлять действиями агента.

### Пример

```text
GOAL: подготовить печатные материалы Fleissig Reinigung.
DELIVERABLE:
- business card PDF 85x55 mm, 2 стороны;
- A6 flyer PDF, 2 стороны.
HARD CONSTRAINTS:
- print-ready;
- 3 mm bleed;
- реальные контакты;
- оригинальный логотип Fleissig.
EXACT ASSETS:
- public/logo-transparent.png;
- реальные QR-коды.
ACCEPTANCE:
- PDF существует;
- размеры и страницы правильные;
- логотип оригинальный;
- QR сканируется;
- каждая страница визуально проверена.
```

## 2. IMMUTABLE DELIVERABLE LOCK

Формат и тип конечного результата нельзя незаметно подменять.

Запрещённые подмены без прямого разрешения пользователя:
- PDF → PNG/mockup;
- DOCX → текст в чате;
- рабочий сайт → скриншот;
- код → концепт или псевдокод;
- редактируемый файл → плоская картинка;
- готовый артефакт → описание того, как его сделать.

Промежуточные превью допустимы только как этап проверки.

Если пользователь запросил конкретный файл, Definition of Done включает существование именно этого файла.

---

## 3. ARTIFACT LOCK

Для задач создания файлов отдельно зафиксируй:
- тип файла;
- количество файлов;
- размеры/формат страниц;
- количество страниц/сторон;
- bleed/safe zone, если требуется;
- редактируемость, если требуется;
- конкретные исходные ассеты;
- конечную пригодность (print-ready, upload-ready, deployable и т.п.).

Если инструмент не способен создать требуемый конечный артефакт, он не может быть главным инструментом исполнения.

Пример: image generation можно использовать для иллюстрации внутри PDF, но нельзя использовать как замену самому PDF.

---

## 4. EXACT ASSET LOCK

Если пользователь требует конкретный существующий ассет, разрешено использовать только оригинал:
- логотип;
- фото;
- QR-код;
- документ;
- таблицу;
- шаблон;
- фирменный элемент;
- файл из репозитория.

Без прямого разрешения пользователя запрещено:
- перерисовывать;
- генерировать аналог;
- реконструировать по памяти;
- заменять визуально похожим;
- использовать placeholder и выдавать его за финальный результат.

Если оригинал недоступен, это BLOCKER.

Правильная реакция:

```text
Exact asset unavailable
→ остановить ветку, где нужна подмена
→ получить/материализовать/найти оригинал
→ продолжить исходный workflow
```

Неправильная реакция:

```text
Exact asset unavailable
→ сгенерировать похожий
→ закончить задачу
```

---

## 5. CORRECTED CONSTRAINT = HARD CONSTRAINT

Если пользователь один раз исправил конкретный пункт, он автоматически получает максимальный приоритет.

После исправления нельзя повторно «творчески интерпретировать» этот пункт.

Пример:

```text
User: «Используй наш настоящий логотип»
```

После этого любой сгенерированный или перерисованный логотип запрещён, даже если выглядит лучше.

Повторение уже исправленной ошибки считается провалом workflow-контроля, а не обычной неточностью.

---

## 6. TOOL-TO-GOAL GATE

Перед каждым существенным tool-call проверь:

```text
1. Какой acceptance criterion этот вызов закрывает?
2. Приближает ли он конечный deliverable?
3. Не меняет ли он hard constraint ради удобства инструмента?
```

Если невозможно назвать criterion, который закрывает tool-call, не делай его, кроме диагностики blocker.

### Tool substitution test

Если выбранный инструмент не умеет выполнить hard constraint:
- сменить инструмент;
- или решить blocker;
- но не менять требование пользователя.

---

## 7. BLOCKER RESET

При технической проблеме не импровизируй новый конечный результат.

Протокол:

```text
BLOCKER
→ RESET TO TASK LOCK
→ определить заблокированный criterion
→ решить именно blocker
→ RESUME
```

Запрещённый паттерн:

```text
BLOCKER
→ SUBSTITUTE
→ FINISH SOMEHOW
```

Типичный пример completion bias:

```text
Не удалось загрузить оригинальный логотип
→ вместо этого сгенерировать похожий
```

Это нарушение Exact Asset Lock.

---

## 8. SCOPE DRIFT DETECTOR

Если по пути обнаружена новая проблема или идея, спроси:

> Блокирует ли она исходный deliverable?

Если да — решить.

Если нет — кратко отметить и оставить вне текущего scope.

Не переключать основную задачу на:
- SEO-проблемы при исправлении формы;
- редизайн всего сайта при правке одной страницы;
- новый формат маркетинга при подготовке конкретного PDF;
- побочный баг, не мешающий requested outcome.

---

## 9. PRE-DELIVERY VERIFICATION GATE

Перед словами «готово», «сделано», «исправлено», «выложено» отдельно проверить конечный результат.

### Content
- весь обязательный текст присутствует;
- имена, контакты, цены и цифры проверены;
- placeholders отсутствуют.

### Assets
- использованы именно требуемые исходники;
- exact assets не заменены;
- версия ассета соответствует источнику.

### Format
- правильный тип файла;
- правильные размеры;
- правильное количество страниц/сторон;
- bleed/safe zone соблюдены, если нужны.

### Functional
По применимости:
- QR сканируется;
- ссылки работают;
- формы отправляются;
- формулы считаются;
- код запускается;
- build/deploy проходит.

### Visual
Для визуальных артефактов:
- отрендерить конечный файл;
- просмотреть каждую страницу/сторону;
- проверить обрезку, наложения, читаемость и иерархию.

### Final question

Перед выдачей спросить себя:

> Если пользователь сравнит результат со своим исходным запросом буквально, выполнен ли каждый hard constraint?

Если нет — задача не завершена.

---

## 10. DEFINITION OF DONE

```text
DONE = requested outcome
     + requested format
     + hard constraints
     + exact assets
     + acceptance verification
```

Не считать задачей выполненной:
- хороший mockup вместо requested file;
- концепт вместо implementation;
- похожий asset вместо exact asset;
- частичный результат без явного обозначения его как partial.

## 11. SKILL ORCHESTRATION

Этот skill применяется как верхний guardrail, а не заменяет профильные skills.

Порядок для нетривиальной задачи:

```text
1. task-lock-scope-control
2. профильный skill (design, research, ads, writing, legal, coding...)
3. execution tools
4. task-lock-scope-control: verification gate
```

Не создавать лишний orchestration overhead для простых вопросов.

---

## 12. FAILURE LEARNING

Если пользователь указывает на ошибку исполнения:
1. определить, какой lock/gate должен был её предотвратить;
2. не ограничиваться извинением;
3. обновить workflow или eval, если класс ошибки повторяемый;
4. повторить задачу только после восстановления Task Lock.

Типовые классы провала:
- deliverable substitution;
- exact asset substitution;
- scope drift;
- tool mismatch;
- incomplete verification;
- completion bias;
- repeated corrected-constraint violation.

## Короткая рабочая формула

```text
LOCK → EXECUTE → RESET ON BLOCKER → VERIFY → DELIVER
```
